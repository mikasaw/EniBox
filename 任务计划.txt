# Enigma Virtual Box 虚拟文件打包工具——开发任务规划


## 一、项目概述

本项目旨在开发一款类似 Enigma Virtual Box 的虚拟文件打包工具，将应用程序及其所有依赖文件（DLL、资源文件、配置文件等）打包成单一可执行文件，运行时在内存中模拟文件系统，不释放任何临时文件到硬盘。

**核心目标：**
- 将任意 Windows 应用程序及依赖文件打包为单个 EXE
- 运行时在内存中模拟文件访问，零磁盘释放
- 支持 x86 和 x64 架构
- 支持文件压缩以减小打包体积
- 提供图形化界面便于操作


## 二、核心架构设计

### 2.1 系统整体架构

本工具由 **两大核心组件** 构成：

| 组件 | 职责 |
|------|------|
| **打包器（Packer）** | 将主程序和所有依赖文件整合到单个可执行文件中，生成带虚拟文件系统的 PE 文件 |
| **加载器（Loader / 外壳）** | 在程序运行前加载，挂钩系统 API，拦截文件访问请求并重定向到内存中的虚拟文件系统 |

### 2.2 虚拟文件系统（VFS）结构

打包后的可执行文件采用分层结构，可划分为三个逻辑区域：

1. **元数据区**：存储虚拟文件系统的目录结构、文件名、路径映射关系、压缩信息
2. **压缩数据区**：包含所有被封装文件的实际内容（可选择压缩存储）
3. **执行头（Loader）**：负责运行时解压和内存加载逻辑，包含 API Hook 代码

### 2.3 PE 文件修改机制

打包器需要修改原始可执行文件的 PE 结构：

- 在原始 EXE 中添加新的 Section，用于存储 VFS 数据和加载器代码
- 修改程序入口点（Entry Point），使其先执行加载器外壳代码再跳转到原始入口
- 调整导入表、重定位表及可能的 TLS 回调


## 三、分阶段开发任务

### 阶段一：技术预研与工具选型（1-2 周）

#### 任务 1.1：深入理解 PE 文件格式
- 研究 PE 文件结构：DOS 头、NT 头、Section 表、导入表（IAT）、导出表、重定位表
- 掌握如何添加新的 Section 而不破坏原有程序
- 理解 PE 文件的入口点修改方式

#### 任务 1.2：掌握 API Hook 技术
核心 Hook 函数（拦截文件系统访问）包括：

| 类别 | 需Hook的函数 |
|------|-------------|
| 文件打开/创建 | `CreateFileA/W`、`NtCreateFile`、`NtOpenFile` |
| 文件读取 | `ReadFile`、`NtReadFile` |
| 文件属性查询 | `GetFileAttributesA/W`、`GetFileSize`、`FindFirstFileA/W`、`FindNextFileA/W` |
| 文件映射 | `CreateFileMapping`、`MapViewOfFile` |
| 注册表访问 | `RegOpenKeyExA/W`、`RegQueryValueExA/W` 等 |

主要 Hook 技术可选方案：
- **IAT Hook**：修改目标进程导入表中的函数地址，实现简单，但存在稳定性问题
- **Inline Hook**：直接修改目标函数的前几个字节，跳转到自定义函数，更稳定
- **Detours 库**：微软官方提供的 API Hook 库，成熟稳定

#### 任务 1.3：选择开发技术栈

**推荐方案：**

| 组件 | 技术选型 | 说明 |
|------|---------|------|
| 打包器（GUI） | C# / WPF 或 C++ / Qt | 跨平台性好，GUI 开发效率高 |
| 加载器（Loader DLL） | C/C++ | 需要底层操作，必须用原生代码 |
| PE 解析与修改 | C/C++（自研或使用 pe-parse 等库） | 核心底层能力 |
| API Hook 库 | Detours / MinHook / EasyHook | 推荐 MinHook（轻量开源） |
| 压缩算法 | LZMA / Zlib / LZ4 | LZMA 压缩率高，LZ4 解压速度快 |

### 阶段二：Loader 加载器开发（3-4 周）

这是整个项目的**核心难点**。

#### 任务 2.1：Loader DLL 框架搭建
- 编写一个 DLL，在 `DllMain` 的 `DLL_PROCESS_ATTACH` 事件中执行初始化
- 初始化包括：解析 VFS 元数据、构建内存中的文件索引、安装 API Hook
- 需要注意 `DllMain` 中的调用限制（不能调用 LoadLibrary 等函数）

#### 任务 2.2：VFS 数据索引构建
- 在内存中建立哈希表或红黑树，存储虚拟文件路径到数据块的映射关系
- 数据结构至少包含：虚拟路径、数据偏移、数据大小、压缩标志、文件属性

```
struct VirtualFileEntry {
    wchar_t* virtual_path;      // 虚拟路径
    uint64_t data_offset;       // 在打包数据中的偏移
    uint32_t data_size;         // 原始数据大小
    uint32_t compressed_size;   // 压缩后大小（0表示未压缩）
    uint32_t file_attributes;   // 文件属性
    uint64_t creation_time;     // 创建时间
    // ...
};
```

#### 任务 2.3：实现文件操作 API Hook
对每个需要拦截的 API，实现对应的回调函数。以 `CreateFileW` 为例：

1. 拦截原 `CreateFileW` 调用
2. 检查请求的文件路径是否在 VFS 索引中
3. 如果命中，返回一个模拟的文件句柄（从自定义句柄池分配）
4. 如果未命中，调用原始 `CreateFileW` 访问真实文件系统
5. 维护句柄状态表，记录每个模拟句柄对应的虚拟文件信息，供后续 `ReadFile` 等操作使用

#### 任务 2.4：实现注册表虚拟化（可选）
- 拦截注册表相关 API（`RegOpenKeyEx`、`RegQueryValueEx` 等）
- 将特定注册表项重定向到内存中的虚拟注册表

#### 任务 2.5：实现子进程注入
Enigma Virtual Box 支持子进程虚拟化。当被包装程序创建子进程时，Loader 需要自动注入到子进程中：
- Hook `CreateProcessA/W` 系列函数
- 在子进程创建后，使用 DLL 注入技术将 Loader DLL 注入子进程
- 注意处理 x86/x64 架构匹配问题

### 阶段三：打包器开发（3-4 周）

#### 任务 3.1：PE 文件解析与修改模块
- 读取原始 EXE 的 PE 结构
- 添加新的 Section 用于存储 VFS 数据和 Loader DLL
- 修改程序入口点，使其先执行 Loader 初始化代码
- 修改导入表，确保 Loader DLL 在程序启动时被加载

#### 任务 3.2：文件收集与 VFS 构建
- 从用户选择的主 EXE 出发，自动收集依赖文件（DLL、资源等）
- 遍历用户指定的文件夹，构建完整的虚拟目录树
- 保留原始目录结构信息

#### 任务 3.3：数据压缩与加密
- 对文件内容进行压缩（推荐 LZMA，压缩率高）
- 将压缩后的数据连同元数据打包为二进制块
- 设计元数据格式（建议使用二进制格式以提高效率，也可选择 JSON/Protobuf）
- （可选）添加简单的加密/混淆保护

#### 任务 3.4：打包文件生成
- 将 Loader DLL 嵌入原 EXE（作为资源或新的 Section）
- 将 VFS 数据块附加到 EXE 末尾或嵌入新 Section
- 更新 PE 头中的各项校验值
- 写入入口点跳转代码（Stub Code）

### 阶段四：图形界面开发（2-3 周）

#### 任务 4.1：主界面设计
参考 Enigma Virtual Box 的操作流程：

- **主程序选择**：浏览并选择待打包的 EXE 文件
- **输出路径设置**：指定打包后文件保存位置
- **文件/文件夹添加**：添加需要封装的其他文件
  - 支持添加单个文件
  - 支持递归添加整个文件夹
  - 支持设定虚拟路径
- **文件选项**：压缩开关、虚拟化开关等
- **执行封包**：一键打包

#### 任务 4.2：功能扩展
- 拖拽添加文件
- 打包进度显示
- 错误日志与提示
- 中英文界面支持
- 命令行支持（供 CI/CD 集成使用）

### 阶段五：兼容性测试与优化（2-3 周）

#### 任务 5.1：兼容性测试
需要覆盖的测试场景：
- **操作系统版本**：Windows 7/8/10/11，Windows Server 各版本
- **架构支持**：x86（32位）和 x64（64位）
- **文件类型**：DLL、OCX、配置文件（.ini/.xml/.json）、多媒体文件、字体文件等
- **应用类型**：普通 Win32 应用、.NET 应用、Qt 应用、Python（PyInstaller 打包后）程序等

#### 任务 5.2：边界情况处理
- 程序使用绝对路径访问文件
- 程序使用 `GetModuleFileName` 等获取自身路径
- 程序依赖注册表项
- 子进程创建与注入
- 异常崩溃时的资源清理
- 与杀毒软件的兼容性（避免误报）

#### 任务 5.3：性能优化
- 内存占用优化（大文件的流式读取而非全量加载）
- 启动速度优化（延迟解压 vs 预解压）
- 压缩率与解压速度的平衡选择

### 阶段六：文档与发布（1 周）

#### 任务 6.1：编写文档
- 使用说明文档（含截图）
- 技术文档（架构说明、二次开发指南）
- 版本更新日志

#### 任务 6.2：发布准备
- 代码开源（GitHub/Gitee）
- 发布 Release 版本
- 编写项目 README


## 四、关键技术难点

| 难点 | 说明 | 建议方案 |
|------|------|---------|
| **PE 文件修改** | 添加 Section 和修改入口点涉及底层 PE 格式 | 使用成熟的 PE 解析库，充分测试各种编译器生成的 EXE |
| **API Hook 稳定性** | IAT Hook 可能导致某些进程崩溃 | 优先采用 Inline Hook 或 Detours，做好异常处理 |
| **子进程注入** | 需要监控进程创建并注入 DLL，涉及安全性问题 | 注意 UAC 和杀软兼容性 |
| **x64 兼容性** | 64位程序的 Hook 实现更复杂（需处理 RIP 相对寻址等） | 使用支持 x64 的 Hook 库（如 MinHook） |
| **杀毒软件误报** | 打包后的文件可能被识别为可疑程序 | 使用合法数字签名、避免敏感 API 调用模式 |
| **架构匹配** | 32位打包器处理64位程序时的兼容问题 | 32位打包器可以生成64位程序，但 Loader DLL 必须匹配目标架构 |

## 六、开发里程碑时间线

| 阶段 | 工期 | 里程碑交付物 |
|------|------|-------------|
| 阶段一：技术预研 | 1-2 周 | 技术选型文档、原型验证代码 |
| 阶段二：Loader 开发 | 3-4 周 | 可工作的 Loader DLL（支持基础文件 Hook） |
| 阶段三：打包器核心 | 3-4 周 | 命令行打包工具（可从命令行生成打包文件） |
| 阶段四：GUI 开发 | 2-3 周 | 完整的图形界面打包工具 |
| 阶段五：测试优化 | 2-3 周 | 测试报告、兼容性修复 |
| 阶段六：文档发布 | 1 周 | 使用文档、开源发布 |
| **总计** | **约 12-17 周** | |

如果团队规模较小或仅有单人开发，建议先以 MVP（最小可行产品）为目标：实现基本的打包（阶段二+阶段三核心功能），后续再逐步完善 GUI 和高级特性。MVP 版本预计可在 6-8 周内完成核心功能。
